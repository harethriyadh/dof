PASSWORD UPDATE / CHANGE - BACKEND SPEC
======================================

Purpose
-------
This document is a backend implementation specification for adding a secure, reliable, and compatible password-change endpoint to the DOF system. The goal is to provide a complete reference an AI agent or backend developer can follow to implement the feature, including API shape, validation, security, token handling, database considerations, tests, logging, and deployment notes.

Summary / High-level decision
----------------------------
- New dedicated endpoint: POST /api/auth/change-password (preferred)
  - Requires Authorization: Bearer <token>
  - Requires current password + new password (and new password confirmation)
  - Verifies current password against stored hash using bcrypt (or Argon2), then updates hash
  - Increments a token version or updates password_changed_at to invalidate existing tokens, and returns a new JWT optionally

Rationale: A separate endpoint is more secure and clearer than trying to make PUT /api/auth/profile also change passwords. It allows different validation, rate-limiting, and flows (require current password).

API: Endpoint design
--------------------
1) POST /api/auth/change-password
   - Auth: Protected (JWT in Authorization header)
   - Content-Type: application/json
   - Request body:
     {
       "current_password": "currentPass123",
       "new_password": "NewPass!2025",
       "confirm_password": "NewPass!2025"
     }

   - Response (success, HTTP 200):
     {
       "success": true,
       "message": "Password changed successfully",
       "data": {
         "token": "<new-jwt-optional>",
         "user": { /* user object without sensitive fields */ }
       }
     }

   - Response (errors): use HTTP codes with body:
     400 Bad Request (validation error)
     401 Unauthorized (invalid/missing token / current password wrong)
     429 Too Many Requests (rate limiting)
     500 Internal Server Error

     Example error response:
     {
       "success": false,
       "message": "Current password is incorrect"
     }

2) Alternative routes (optional):
   - PUT /api/auth/password -- similar semantics
   - POST /api/auth/reset-password (for token-based reset via email) - separate flow

Security & Validation
---------------------
- Authorization: require valid JWT and user id extraction (userId) from token.
- Verify the current password using bcrypt.compare (or Argon2 equivalent) in constant time.
- Validate new password:
  - Minimum length: 8 characters (recommend 12 for higher security)
  - Optional complexity: require mixed-case letters, digits, symbols (configurable)
  - Recommend using zxcvbn or similar to reject weak passwords (if available)
  - Ensure new_password === confirm_password
  - Prevent reusing recent passwords: check hash against password history (if implemented)
  - Do not accept new_password equal to current password (value equality check)
- Rate limiting and lockout:
  - Per-user throttling for change-password attempts (e.g., max 5 attempts / 15 minutes)
  - For repeated failures, implement temporary account lockout or exponential backoff and notify user/admin
- Password hashing:
  - Use bcrypt with work factor 12-14, or Argon2id (preferred if available)
  - Never store plaintext passwords
- Token invalidation:
  - Option A: maintain a `tokenVersion` integer on user document. Include `tokenVersion` in JWT. On password change increment tokenVersion so previous tokens become invalid.
  - Option B: set `password_changed_at` timestamp and validate JWT issue time (iat) against it: if iat < password_changed_at => token invalid
  - Option C: maintain a server-side token revocation list (less scalable)
  - Prefer Option A or B for stateless JWT invalidation.
- Logging & monitoring:
  - Log events for password change attempts (success/failure) with user id, IP, user agent.
  - Do NOT log password contents.
  - Emit metrics for change-password successes/failures for monitoring.
- Email notification:
  - Send an email to the user after a successful password change (security notice). Include time and IP of request.
  - Provide a rollback / support process in case of unauthorized change.

Database changes (if necessary)
-------------------------------
- User schema (Mongo/Mongoose example):
  {
    _id,
    username,
    full_name,
    password: String, // bcrypt/argon2 hash
    password_changed_at: Date,
    tokenVersion: Number, // optional
    password_history: [{ hash: String, changedAt: Date }], // optional
    ...other fields
  }

- Migration notes:
  - If adding tokenVersion or password_history, migrate existing users to tokenVersion:0 and empty history.
  - If password_history is used, store last N (e.g., 5) hashes to prevent reuse.

Controller pseudo-code (Node.js / Express style)
------------------------------------------------
// imports: bcrypt or argon2, jwt, models, validators, rate-limit helpers

async function changePasswordHandler(req, res) {
  const userId = req.user?.id; // from JWT middleware
  const { current_password, new_password, confirm_password } = req.body;

  // Basic validation
  if (!current_password || !new_password || !confirm_password) {
    return res.status(400).json({ success: false, message: 'All fields are required' });
  }
  if (new_password !== confirm_password) {
    return res.status(400).json({ success: false, message: 'Password confirmation does not match' });
  }
  if (new_password.length < 8) {
    return res.status(400).json({ success: false, message: 'Password must be at least 8 characters' });
  }

  // Rate limit check – per user
  if (await isRateLimited(userId)) {
    return res.status(429).json({ success: false, message: 'Too many attempts. Try again later.' });
  }

  const user = await User.findById(userId).select('+password');
  if (!user) return res.status(401).json({ success: false, message: 'Unauthorized' });

  // verify current password
  const matches = await bcrypt.compare(current_password, user.password);
  if (!matches) {
    await recordFailedAttempt(userId);
    return res.status(401).json({ success: false, message: 'Current password is incorrect' });
  }

  // check new password != old password
  const newEqualsOld = await bcrypt.compare(new_password, user.password);
  if (newEqualsOld) {
    return res.status(400).json({ success: false, message: 'New password must be different from current password' });
  }

  // Optional: check password history to prevent reuse
  if (user.password_history) {
    for (const ph of user.password_history) {
      if (await bcrypt.compare(new_password, ph.hash)) {
        return res.status(400).json({ success: false, message: 'New password was used recently. Choose a different password.' });
      }
    }
  }

  // Hash and save new password
  const newHash = await bcrypt.hash(new_password, 12); // tune cost

  // Wrap DB update in transaction if supported (e.g., Mongo with session)
  user.password = newHash;
  user.password_changed_at = new Date();
  // push into password_history (limit to N)
  if (!user.password_history) user.password_history = [];
  user.password_history.unshift({ hash: newHash, changedAt: new Date() });
  user.password_history = user.password_history.slice(0, 5);

  // increment tokenVersion or update timestamp for invalidating old JWTs
  if (typeof user.tokenVersion === 'number') {
    user.tokenVersion += 1;
  }

  await user.save();

  // optional: create a new JWT including tokenVersion (or rely on iat/password_changed_at check)
  const token = generateJwt({ id: user._id, tokenVersion: user.tokenVersion });

  // send security email notice
  sendPasswordChangeEmail(user.email, { time: new Date(), ip: req.ip });

  return res.json({ success: true, message: 'Password changed successfully', data: { token, user: sanitizeUser(user) } });
}

JWT validation middleware must then check tokenVersion or compare iat with password_changed_at to reject old tokens.

Payload & Token handling
------------------------
- JWT should include user id and tokenVersion (if using tokenVersion approach):
  {
    sub: user._id,
    iat: <timestamp>,
    tv: user.tokenVersion
  }
- On each protected request the middleware must fetch user tokenVersion and compare with jwt.tv (or check password_changed_at > jwt.iat) and reject if mismatch.

Errors & status codes
---------------------
- 200: success
- 400: validation errors (missing fields, weak password, confirmation mismatch)
- 401: current password incorrect or invalid auth
- 403: forbidden (if additional restrictions apply)
- 429: too many attempts
- 500: server error
- Error body format must be consistent with existing API: { success: false, message: '...' } or { success:false, errors: [...] }

Testing & QA
------------
- Unit tests:
  - success case: correct current password -> new password saved, tokenVersion incremented, email sent
  - wrong current password -> 401
  - weak new password -> 400
  - reuse of old password -> 400 (if password_history implemented)
  - JWT invalidation: previous token should be rejected after change
- Integration tests:
  - full flow with login -> change password -> old token rejected -> login with new password works
  - concurrency tests for simultaneous requests (ensure single update wins, use transactions)
- Manual QA:
  - test both successful and failed attempts, check email notifications and logs

Operational & Deployment notes
------------------------------
- Ensure TLS always used in production.
- Rate limiting: configure per user (and per IP) limits. 5 attempts / 15 minutes is a reasonable default.
- Monitoring: create an alert for change-password failure spikes and successful changes.
- Logging: include audit logs for security team review; redact sensitive data.

Backward compatibility & frontend interactions
---------------------------------------------
- Frontend should call POST /api/auth/change-password with current_password and new_password.
- After success, frontend should replace stored token (if returned) with the new token; otherwise force the user to re-login.
- If backend prefers to not return a new token, set password_changed_at and have frontend prompt re-login.
- If the frontend still uses PUT /api/auth/profile for other updates, keep that separate and do not attempt to add password fields there (unless server updates are made accordingly).
